05｜堆疊與佇列：從配對到單調候選

在程式設計中，面對需要「暫停當前手邊工作、優先解決最近發生的巢狀事件」時，我們會自然聯想到堆疊（Stack）；而面對需要「遵循抵達先後、公平排隊依序處理」的任務時，佇列（Queue）則是不可或缺的基石。然而，當問題進一步要求「在陣列中以線性時間尋找下一個更大元素」，或是「在持續滑動的視窗中即時維護極值」時，我們就需要將這兩種結構昇華為強大的「單調結構」：在遍歷的每一步中，精準辨識出哪些舊元素已經找到了答案、哪些歷史候選已經被新生力量永久支配而可以被安全淘汰。本章將從基本操作出發，一步步推導單調堆疊與單調佇列的核心不變量，並用平攤分析證明它們優異的線性時間複雜度。

學習目標：清楚分辨後進先出（LIFO）與先進先出（FIFO）的適用場景；深刻理解括號配對為何必須比對堆疊頂端而非全域計數；在面對重複元素時能正確拿捏嚴格與非嚴格的大小比較；並能夠用平攤分析（Amortized Analysis）嚴謹證明單調堆疊與單調佇列的總工作量為 O(n)。除特別標註外，數值計算皆採固定大小整數模型。

1. 兩種等待規則，兩種 Python 容器

堆疊（Stack）遵循後進先出（LIFO, Last-In First-Out）的哲學：最新加入的元素擁有最先被處理的特權；放入資料稱為 push（在 Python 中對應 append），取出最近加入的資料則稱為 pop。相較之下，佇列（Queue）遵循先進先出（FIFO, First-In First-Out）的公平原則：元素永遠從尾端依序排入，並從頭端依序取出。這兩種都是高層次的抽象資料型態（ADT），並不限定底層的實體儲存形式。在 Python 中，堆疊通常直接以原生的動態陣列 list 實作；而佇列則強烈建議採用標準函式庫中的 collections.deque（雙端佇列）。

from collections import deque

stack = []
stack.append("A")
stack.append("B")
assert stack.pop() == "B"

queue = deque(["A", "B"])
queue.append("C")
assert queue.popleft() == "A"
assert queue[0] == "B"
Python 常見容器在堆疊與佇列操作上的時間複雜度比較
具體操作漸近計算成本底層原理與注意事項
list.append() 與末端 pop()平攤 O(1)在動態陣列尾端操作極快，僅在偶發擴容時需要搬移參照
list.pop(0) 與 list.insert(0, v)O(n)嚴格禁止用於佇列！每次從頭端彈出，後續所有元素參照都必須向左平移一格
deque.append()、pop()、appendleft()、popleft()嚴格 O(1)底層由雙向鏈結的定長記憶體區塊（Chunk）組成，雙端增刪皆保證常數時間
deque 的頭尾端點查看（queue[0]、queue[-1]）O(1)頭尾指標可直接定位
在 deque 中依隨機下標讀取或刪除中間元素最壞 O(n)非連續陣列，需要沿著內部區塊逐一尋訪，並非 deque 的專長

在工程防禦上，對空容器執行 pop() 或 popleft() 都會直接拋出 IndexError 異常，實作時應依題目規格事先檢查 bool(container) 或做好邊界防護。另外，deque 支援傳入 maxlen=k 參數來建立固定容量的環形歷史緩衝區，滿載時新元素進入會自動將另一端的舊元素靜默擠出；但在實現圖的廣度優先搜尋（BFS）或維護單調候選時，請確保使用無容量上限的 deque，以防尚未處理的關鍵節點被意外丟棄。在第 06 章中，我們將大量依賴 deque 的 FIFO 特性來實現圖與樹的層序遍歷。

2. 括號配對：最近開啟者必須最先關閉

輸入由 ()、[]、{} 六種字元組成的字串，判斷括號的種類與巢狀開閉順序是否完全合法配對。若輸入為空字串視為合法回傳 True；若出現六種括號以外的非法字元則拋出 ValueError。

LeetCode 20 · Valid Parentheses

當我們由左至右掃描字串時，每當遇到一個開括號，代表開啟了一個新的作用域，我們將其壓入堆疊暫存；而當遇到閉括號時，它所期望關閉的，必須是當前「距離它最近、且尚未關閉的那個開括號」——這剛好完美對應到堆疊頂端的元素。初學者常誤以為「只要統計各類左右括號的總數相等即可」，這是完全錯誤的；例如字串 "([)]"，每種括號數量各自平衡，但外層的圓括號還沒閉合，中括號就搶先跨越閉合，破壞了階層巢狀結構。在堆疊中，我們絕不能跨越頂端去關閉更深層的括號，因為「最晚開啟的區塊必須最先結束」。

核心不變量：在字串遍歷的每一步，只要當前的前綴子字串依然合法，stack 中由底至頂的元素，精準對應了目前尚未關閉的所有開括號，且嚴格按照由外層到內層的巢狀次序排列。我們可以用一個布林變數 valid 標記是否發生過失配；即便中途發現錯誤，依然可以完整走完字串以利驗證後續字元，並將失配結果忠實傳遞至最終判定。

def valid_brackets(text):
    """只接受六種括號；其他字元拋 ValueError。"""
    partner = {")": "(", "]": "[", "}": "{"}
    stack = []
    valid = True
    for ch in text:
        if ch in "([{":
            stack.append(ch)
        elif ch in partner:
            if not stack or stack[-1] != partner[ch]:
                valid = False
            else:
                stack.pop()
        else:
            raise ValueError("輸入只能包含括號")
    return valid and not stack

設字串長度為 n，演算法只需單次線性遍歷，時間複雜度為 O(n)；最壞空間複雜度為 O(n)（例如輸入全為開括號）。若已知括號的最大巢狀深度為 d，在合法情況下堆疊所需空間可更精準描述為 O(d)。

3. 表達式解析：逆波蘭式與運算元順序

輸入代表逆波蘭表示法（Reverse Polish Notation, RPN）的字串清單，內容由整數或四則運算子 +、-、*、// 組成，回傳最終求值結果。例如輸入 ["8", "3", "-", "2", "*"] 回傳 10。若運算式不完整拋出 ValueError，除以零拋出 ZeroDivisionError。

LeetCode 150 · Evaluate Reverse Polish Notation 原題採用浮點數除法並向零截斷；本節實作採用 Python 內建的 // 向下取整。例如對於 −7 除以 3，兩者分別會得到 −2 與 −3。

一般我們習慣的中綴表達式（如 (8 − 3) × 2）需要依賴括號與運算子優先級規則；而逆波蘭式（後綴表達式）則精妙地將運算子直接置於其作用的兩個運算元之後，徹底消除了括號的歧義。解析的規則非常單純：遇到數字就將其數值 push 存入堆疊；每當讀到運算子時，立刻從堆疊頂部彈出兩個已經算好的子運算結果進行計算，並將產生的新結果重新 push 回堆疊中。

def evaluate_rpn(tokens):
    """逆波蘭式整數運算，// 採 Python 向下取整。"""
    stack = []
    for token in tokens:
        if token not in {"+", "-", "*", "//"}:
            stack.append(int(token))
            continue
        if len(stack) < 2:
            raise ValueError("運算元不足")
        b, a = stack.pop(), stack.pop()
        if token == "+":
            stack.append(a + b)
        elif token == "-":
            stack.append(a - b)
        elif token == "*":
            stack.append(a * b)
        else:
            stack.append(a // b)
    if len(stack) != 1:
        raise ValueError("運算式不完整")
    return stack[0]

核心不變量與操作細節：stack 時刻保存著「在已處理的前綴中，尚未被後續運算子消耗掉的子表達式數值」。這裡有一個最經典的操作順序陷阱：第一個 pop() 出來的變數 b 是運算子的「右運算元」，第二個 pop() 出來的變數 a 才是「左運算元」！在計算減法或除法時，必須嚴格執行 a − b 與 a // b。如果把順序顛倒寫成 b − a，在加法與乘法的單元測試中因為交換律完全看不出破綻，卻會在減法與除法上引發致命錯誤。以 "8 3 −" 為例，堆疊狀態依序為 [8] → [8, 3] → 彈出 3 與 8 執行 8 − 3 → 壓入結果 [5]。

本實作明確採用 Python 標準的 // 整數除法向下取整規則，因此 −7 // 3 的結果為 −3。若題目規格要求向零截斷（C/C++ 風格），可透過 int(a / b) 或先取絕對值相除後再根據正負號還原。在合約邊界上，遇到除以零直接觸發 ZeroDivisionError；若遇到運算子時堆疊不足兩個元素，或是全域運算結束後堆疊中殘留超過一個元素，皆屬於語法不完整的非法表達式，應拋出 ValueError。

設 token 總數為 t，所有項目在堆疊中各進出一次，總時間複雜度為 O(t)，堆疊輔助空間為 O(t)。若處理大整數運算，字串轉整數與大數乘除的耗時應按位元長度另計。

4. 單調堆疊：下一個嚴格較大元素

LeetCode 739 · Daily Temperatures 原題求等待天數，無解填 0。本節實作先行求解「右側下一個較大元素的具體索引」，無解填 −1；一旦求得目標索引 j，等待天數直接等於 j − i。

問題說明：對於陣列中的每一個索引 i，請找出在其右側第一個數值嚴格大於 values[i] 的索引位置；若右側完全沒有更大的數值，則該位置填入 −1。如果採用雙層迴圈對每個元素向右暴力搜尋，最壞時間複雜度為 O(n²)。要想在線性時間內解決，我們必須轉換視角：不要讓過去的元素苦苦向右搜尋，而是讓新讀入的元素主動去「認領」那些在過去歷史中一直在等待它的元素！

我們在 stack 中存放尚未找到答案的索引，並維持強大的幾何單調性：堆疊內部的索引嚴格單調遞增，且其所對應的陣列數值由底至頂呈現「非遞增」排列。當前掃描到數值 value 時，如果當前堆疊頂端所對應的數值嚴格小於 value，這說明了什麼？說明了當前這個 value 正是頂端索引朝思暮想的「右側第一個更大值」！此時我們果斷將頂端 pop 出來並在答案陣列中記錄當前索引 i；隨後繼續檢查新的堆疊頂端，直到頂端數值不小於 value 為止，最後再將當前索引 i 壓入堆疊。請注意：相等數值無法滿足「嚴格較大」的合約，因此會被安全保留在堆疊中。

def next_greater_indices(values):
    answer = [-1] * len(values)
    stack = []  # 未找到右側「嚴格較大」值的索引。
    for i, value in enumerate(values):
        while stack and values[stack[-1]] < value:
            answer[stack.pop()] = i
        stack.append(i)
    return answer

平攤複雜度證明：程式碼外觀上是 for 迴圈內套了 while 迴圈，許多初學者會直覺誤以為它是 O(n²)。但請站在陣列元素的生命週期來思考：陣列中的每一個索引，在整個演算法生命週期中都恰好只會被 push 進入堆疊一次，且一旦被 pop 彈出後就永遠不會再次入棧。這意味著 while 迴圈內部的 pop 述句在全程的執行總次數上限嚴格為 n 次。雖然某些回合（如上述處理 20 時）可能一次性彈出多個元素，但平均分攤下來，每個元素平攤成本僅為 O(1)，整體的總時間複雜度是嚴密保證的 O(n)。

本演算法時間複雜度為 O(n)，輔助空間為 O(n)，輸出空間為 O(n)。最壞空間情況出現在輸入為單調遞減時，所有索引皆會累積在堆疊中。

5. 單調雙端佇列：固定視窗最大值

輸入整數陣列 values 與正整數視窗長度 k，回傳每個大小為 k 的滑動視窗中的最大數值。例如輸入 [4, 1, 3, 3, 0, 5]、k = 3，回傳 [4, 3, 3, 5]；若 k 超出 1 到 len(values) 的合法範圍則拋出 ValueError。

LeetCode 239 · Sliding Window Maximum

在長度為 k 的連續滑動視窗中維護極值時，單調堆疊就顯得力不從心了：因為堆疊只能在一端進行彈出，無法自然地將隨著視窗右移而在左端「過期」的老舊元素淘汰掉。解決之道是採用 collections.deque（單調雙端佇列）：它允許我們從頭端剔除已經滑出視窗的過期索引，同時從尾端淘汰掉被新元素徹底壓制（支配）的無用候選。

三大核心不變量：在每一輪迭代完畢後，佇列中的索引嚴格遞增；所有索引皆保證落在目前的視窗 [i − k + 1, i] 之內；且這些索引所對應的數值由頭至尾呈現「嚴格單調遞減」。每當右端讀入新位置 i 時，演算法分為三步：首先，檢查頭端 candidates[0]，若其索引 ≤ i − k 則代表已滑出視窗過期，執行 popleft()；其次，檢查尾端，若尾端候選的數值 ≤ 當前新值 values[i]，代表它們已被新值徹底支配，從尾端執行 pop()；最後將 i 壓入尾端。當視窗形成滿 k 個元素後，佇列的頭端 candidates[0] 所指的永遠是當前視窗的絕對最大值！

from collections import deque

def sliding_maximum(values, k):
    if not 1 <= k <= len(values):
        raise ValueError("k 必須介於 1 與資料長度之間")
    candidates = deque()  # 索引遞增，對應值嚴格遞減。
    answer = []
    for i, value in enumerate(values):
        while candidates and candidates[0] <= i - k:
            candidates.popleft()
        while candidates and values[candidates[-1]] <= value:
            candidates.pop()
        candidates.append(i)
        if i >= k - 1:
            answer.append(values[candidates[0]])
    return answer

逐步追蹤範例三：輸入 values = [4, 1, 3, 3, 0, 5]，k = 3

當前 i／值頭端過期移除尾端被支配淘汰deque 當前狀態（索引:數值）當前視窗產出最大值
0／4無無[0:4]視窗未滿 3
1／1無無[0:4, 1:1]視窗未滿 3
2／3無淘汰 1:1（因 1 ≤ 3）[0:4, 2:3]4（取頭端）
3／3移除 0:4（因 0 ≤ 3 − 3）淘汰 2:3（因 2 號值 3 ≤ 當前 3）[3:3]3（取頭端）
4／0無無[3:3, 4:0]3（取頭端）
5／5無依序淘汰 4:0 與 3:3[5:5]5（取頭端）

淘汰尾端的支配性定理：為什麼只要 values[j] ≤ values[i]（其中 j < i），舊候選 j 就可以被永久且安全地丟棄？思考視窗的移動過程：在未來任何同時包含 j 的視窗中，因為 i 在 j 的右側，該視窗必然也同時包含 i；而在數值上 i 至少跟 j 一樣大，在存活時限上 i 甚至比 j 更加年輕、更晚過期。換句話說，只要有 i 的存在，舊元素 j 永遠不可能成為任何未來視窗的唯一最大值！這種「數值更大且壽命更長」的壓倒性優勢稱為支配關係（Dominance）。唯有透過嚴密的支配邏輯，我們才能在刪除候選時百分之百確保絕不漏解。

每個索引只會入隊一次，且最多從頭端或尾端出隊一次，總時間複雜度為平攤 O(n)；候選佇列空間至多為 O(k)，輸出空間為 O(n − k + 1)。請特別記住：在佇列中必須存放「索引」而非純數值，否則面對重複元素時將無從判斷哪一個已經過期；同時絕不能拿普通 list 來當佇列呼叫 pop(0)，那會讓演算法直接退化回 O(nk)。

面對失配字串 "([)]"，請回傳第一個無法配對的閉括號索引 2。若字串中沒有失配的閉括號，但最後仍殘留未閉合的開括號，回傳最早未閉合開括號的索引；若完全合法配對則回傳 None。假設輸入字串僅含六種括號。

參考解答

將堆疊存放的項目由純字元改為 (括號字元, 索引位置) 的元組。遇到閉括號時，若堆疊為空或與頂端不符，直接回傳當前索引 i；當字串掃描完畢後若堆疊非空，則回傳 stack[0][1]（即堆疊底部的最早未閉合索引）；若堆疊淨空則回傳 None。

def first_bracket_error(text):
    """只接受括號；回傳第一個無法配對的關閉位置，否則最早未關閉位置。"""
    partner = {")": "(", "]": "[", "}": "{"}
    stack = []
    for i, ch in enumerate(text):
        if ch in "([{":
            stack.append((ch, i))
        elif ch in partner:
            if not stack or stack[-1][0] != partner[ch]:
                return i
            stack.pop()
        else:
            raise ValueError("輸入只能包含括號")
    return stack[0][1] if stack else None

時間複雜度為 O(n)，空間複雜度為 O(n)。測試覆蓋應包含：空字串、第一位就是閉括號、交錯失配以及全是開括號的情境。

練習 B：尋找下一個嚴格較小值的等待跨度

給定輸入陣列 [5, 5, 2, 4, 1]，希望輸出各位置到右側第一個更小元素的步數差距 [2, 1, 2, 1, 0]（0 代表右側無更小值）。請說明如何修改原本的單調堆疊模板。

參考解答

主要進行三處關鍵調整：第一，answer 陣列的預設無解初值由 −1 改為 0；第二，while 迴圈的彈出條件由 values[stack[-1]] < value 改為 values[stack[-1]] > value（堆疊改為維護數值非遞減）；第三，當彈出索引 j 時，記錄的差距值計算為 answer[j] = i − j。對於相同數值依然不觸發彈出以滿足嚴格較小的定義。每個元素進出堆疊各一次，時間複雜度為穩定的 O(n)，空間為 O(n)。

練習 C：滑動視窗最大值改為回傳「最早出現的索引」

對於輸入 [3, 3, 2]、k = 2，每個視窗的最大值位置希望回傳 [0, 1]。原本的程式碼會用較新的 3 淘汰較舊的 3，該如何修改以滿足要求？

參考解答

將尾端淘汰條件由 ≤ 改為嚴格的 <。這樣一來，當遇到數值相同的新元素時，舊元素不會被淘汰，佇列中數值呈現非遞增而非嚴格遞減。在輸出時，直接 append(candidates[0]) 輸出索引而非數值。由於佇列索引天生由小到大排列，頭端永遠會保留目前視窗內最早出現的最大值索引。空間複雜度仍為 O(k)，時間複雜度仍為 O(n)。

7. 決策小結

  • 面對「最近開啟、尚未結束的事件」或具有嚴密階層嵌套結構：毫不猶豫選擇堆疊（Stack）。括號配對、算式求值、以及遞迴轉手動迭代皆屬此類。
  • 面對「嚴格按照到達先後、先來先服務」的排隊場景：使用 collections.deque 配合 append 與 popleft，堅決避免使用低效的 list.pop(0)。
  • 尋找「下一個更大／更小元素」：構建單調堆疊，明確定義是嚴格大小還是允許相等，並搞清楚輸出要的是數值、目標索引還是距離差。
  • 滑動視窗動態維護區間極值：構建單調雙端佇列（Monotonic Deque），頭端專職過濾超時過期元素，尾端專職淘汰被支配候選。
  • 分析巢狀迴圈時：擺脫肉眼看縮排的誤區，聚焦追蹤「每個元素一生到底會被處理並彈出幾次」，以平攤分析證明真正的線性效能。
  • 單調候選結構的核心是剪除永遠不可能成為解答的資訊；如果業務需求改為動態查詢「視窗中位數」或「第 k 大元素」，由於歷史元素隨時可能重返候選，單調佇列的支配前提便不再成立，必須改用雙堆（Two Heaps）或平衡樹。
