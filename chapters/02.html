02｜陣列與字串：用邊界減少重複掃描

在解陣列與字串問題時，效能低落往往來自於對重疊區間進行了大量無意義的重複掃描。要打破這個瓶頸，主要有三種強大的思考工具：雙指標透過有序性大膽排除不可能的候選組合；滑動視窗透過動態維護邊界，把相鄰區間的共有資訊重複利用；前綴和則預先算好各個前綴的累加值，讓原本耗時的區間查詢瞬間化簡為 O(1) 的兩點相減。在實際解題時，關鍵在於先確認資料是否具備單調性或排序、視窗是否能單向推進收縮，以及查詢是單次還是多次重複發起。

本章所稱的「區間」皆指陣列中連續相鄰的元素；而「子序列」則允許跳過中間元素。在回傳區間範圍時，本書統一採用左閉右開的半開區間 [left, right)，其長度剛好等於 right − left。

1. 先約定索引與區間

在長度為 n 的 Python list 中，合法的索引範圍是 0 到 n − 1。雖然 Python 提供了負數索引的便利語法，但在演算法實作中，過度依賴負索引往往容易掩蓋指標意外越界的邏輯缺陷。此外，list 是可原地修改的可變容器，而字串 str 則是不可變物件。值得注意的是，Python 字串的長度與索引是嚴格依照 Unicode 碼位（code point）計算的，並不完全等同於人類肉眼所見的單一字形（例如組合重音字元可能由多個碼位拼成）。若題目涉及嚴格的字形處理，就必須依題意特別定義文字分割規則。

在整個演算法領域中，採用 [left, right) 左閉右開的半開區間表示法能省去極多繁瑣的邊界加減。區間內的元素長度直接等於 right − left；當 left 等於 right 時恰好代表空區間 [i, i)；而相鄰的兩個區間 [a, b) 與 [b, c) 拼接起來，剛好嚴絲合縫地等於 [a, c)。請特別留意一個特例：在後文介紹的兩端夾逼演算法 two_sum_sorted 中，使用的是兩個包含兩端端點的實體元素索引；而在其他涉及連續子陣列的函式中，回傳的都是標準的半開區間，閱讀時請務必分清兩者的合約差異。

在 Python 中，隨手寫下一句 nums[left:right] 切片，底層都會配置記憶體並複製建立一個全新的 list，若切片長度為 k，就需要耗費 O(k) 的時間與空間。相較之下，維護一對整數指標僅僅需要 O(1) 的空間。在撰寫與除錯初期，你可以在小規模測試中將切片印出來確認；但在正式的演算法迴圈中，若每走一步就切片一次或重複呼叫 sum()，原本精妙的線性演算法就會被拖慢成平方時間。

2. 左右夾逼：用排序證明整批排除

LeetCode 167 · Two Sum II - Input Array Is Sorted：原題採 1 起算索引且保證一組解；本節採 0 起算，無解回傳 None。

問題說明：給定一個已經按照非遞減順序排好序的整數陣列，請找出兩個不同位置的元素，使其相加剛好等於 target。只要找出任意一組合法索引即可，若無解則回傳 None。我們讓 left 指向陣列最小值、right 指向最大值。如果兩者相加依然小於 target，這意味著：即使拿目前場上最大的數字來搭檔，總和都依然不足，因此當前的 left 絕不可能跟右側剩餘的任何其他元素配對成功，我們可以毫無懸念地將 left 往右推進排除；反之，若相加太大，就對稱地把 right 往左推進排除。

def two_sum_sorted(nums: list[int], target: int):
    """前置條件：nums 已依非遞減順序排序。回傳兩個不同索引或 None。"""
    left, right = 0, len(nums) - 1
    while left < right:
        current = nums[left] + nums[right]
        if current == target:
            return left, right
        if current < target:
            left += 1
        else:
            right -= 1
    return None

逐步追蹤範例 A：輸入 nums = [−6, −2, 1, 5, 9]，target = 6。

left、right 索引當前元素相加決策動作與推理理由

1、4−2 + 9 = 7總和大於 6，排除不可能有解的 right = 4

核心不變量：如果問題存在合法解，那麼至少有一組解完整落在當前的 [left, right] 閉區間之內。每一次移動指標，背後都有嚴謹的大小單調性作為後盾，因此絕不會誤傷潛在的正解。當迴圈因為 left >= right 終止時，代表陣列中已經不存在兩個不同的位置，可以安心宣告無解。每走一輪，待搜尋區間長度至少減少 1，因此演算法必然會在最多 n 步內終止。

在陣列已預先排序的前提下，雙指標夾逼的時間複雜度為極佳的 O(n)，額外空間為 O(1)。輸入陣列中包含負數或重複元素都不會影響這項正確性。但請牢記：若原始輸入尚未排序，就不能直接盲目套用雙指標；若先花費 O(n log n) 排序，原本題目所要求的初始索引就會被打亂，此時必須額外綁定數值與原始索引。在第 03 章中，我們將學習如何利用雜湊表，在無需排序的情況下於未排序陣列中達到 O(n) 解題。

3. 同向雙指標：讀取與寫入分開

LeetCode 27 · Remove Element：本節另要求保留元素的相對順序。

問題說明：在原陣列上刪除所有等於 unwanted 的元素，同時必須保留其他有效元素的原本相對順序，最後回傳有效長度。我們的策略是把讀取與寫入分工：read 指標依序掃描陣列中的每個原始位置，而 write 指標則永遠指向「下一個等待寫入有效元素的位置」。只有當 read 讀到了值得保留的數值時，才將其寫入 nums[write]，並將 write 往前推進一格。這項合約並不強求底層 list 實體縮容，因此 write 之後的舊資料純屬無效殘留值，不影響正確性。

def remove_value(nums: list[int], unwanted: int) -> int:
    """原地穩定壓縮；僅前 write 個元素是有效輸出。"""
    write = 0
    for read in range(len(nums)):
        if nums[read] != unwanted:
            nums[write] = nums[read]
            write += 1
    return write

核心不變量：在每一輪迭代開始前，前綴 nums[:write] 恰好完整收錄了原始陣列在 read 之前所有應該被保留的元素，且始終維持 write ≤ read 的不等式。這個關鍵關係保證了：每一次的寫入操作，絕對不可能覆蓋掉任何尚未被 read 檢驗過的資料。例如對 [5, 2, 5, 8] 刪除 5，處理完畢後陣列前兩格為 [2, 8]，函式回傳長度 2，後面的元素內容已無關緊要。

本演算法時間複雜度為 O(n)，輔助空間僅需 O(1)。若外部規格要求實體縮小容器尺寸，只需在結尾補上一句 del nums[write:] 即可。在工程實踐中，千萬不要試圖在單一 for 迴圈中直接呼叫 list.remove()，這不僅會導致每次刪除都引發 O(n) 的元素後移，更容易因為索引動態跳動而漏掉相鄰的連續目標值。將讀取與寫入指標分離，是進行各類原地壓縮最穩健的通用模式。

4. 固定視窗：移出一項，再加入一項

給定一系列代表每日收益的整數（可正可負），請找出長度恰好為 k 的連續時段中的最大總收益。如果採用暴力迴圈，對每個可能的起點都重新加總 k 個數字，時間複雜度高達 O((n − k + 1)k)。但觀察相鄰的兩個視窗，它們之間有高達 k − 1 個元素是完全重疊的；因此只要從上一輪的總和中扣掉剛離開視窗的舊元素，再補上新滑入的新元素，就能在 O(1) 內完成狀態更新。

def max_fixed_window_sum(nums: list[int], k: int) -> int:
    if not 1 <= k <= len(nums):
        raise ValueError("k 必須介於 1 與陣列長度之間")
    current = sum(nums[i] for i in range(k))
    best = current
    for right in range(k, len(nums)):
        current += nums[right] - nums[right - k]
        best = max(best, current)
    return best
nums = [4,−2,5,1]，k = 2

[0,2)4 + (−2)22
[1,3)2 − 4 + 533

核心不變量：每次迭代完成後，current 的數值精確等於以 right 結尾、長度恰為 k 的視窗元素總和；而 best 則忠實記錄了截至目前所見過的所有視窗總和的最大值。因為每次滑動只需要一次減法與一次加法，陣列中即使包含負數也完全不受影響。請特別留意：best 必須以第一個完整視窗的和來初始化，如果習慣性寫成 best = 0，當面對全為負數的資料時，就會錯誤回傳不屬於任何視窗的 0。

本演算法的時間複雜度為 O(n)，輔助空間為 O(1)。在初始化第一個視窗時，我們使用生成器表達式配合 sum()，避免了建立多餘的切片複本。固定長度視窗移出元素的時機是由長度 k 強制決定的；而下一節將介紹的可變長度視窗，其移出時機則取決於自訂的業務約束條件。

5. 可變視窗：把單調性寫成前提

LeetCode 1208 · Get Equal Substrings Within Budget：原題將兩字串的字元碼差轉為成本，再求最長長度；本節直接輸入成本陣列並回傳區間。

問題說明：陣列記錄每天的資源消耗（皆為非負整數），請找出累計消耗量不超過 budget 的最長連續天數區間。回傳半開區間，若有多組同長度的最佳解，取出現最早的那一組；若輸入為空或完全沒有合法的非空區間，則回傳 (0, 0)。演算法的運作方式是：右端指針不斷向右吸納新的一天，一旦總消耗超出了 budget，左端指針就必須持續向右吐出元素，直到總和重新降回合法預算內。之所以能這樣做，是因為所有數字皆非負：往右擴張絕不會讓總和變小，從左收縮也絕不會讓總和變大，這種單調性是滑動視窗能正確排除候選的根基。

def longest_budget_window(nums: list[int], budget: int) -> tuple[int, int]:
    """回傳最長合法半開區間；同長時取最早者。僅接受非負整數。"""
    if budget < 0 or any(value < 0 for value in nums):
        raise ValueError("budget 與元素必須非負")
    left = 0
    total = 0
    best = (0, 0)
    for right, value in enumerate(nums):
        total += value
        while total > budget:
            total -= nums[left]
            left += 1
        if right + 1 - left > best[1] - best[0]:
            best = (left, right + 1)
    return best

核心不變量：在 while 收縮結束後，total 精確等於 nums[left:right+1] 的總和且必定 ≤ budget；而且所有小於 left 的起點，以當前 right 為右邊界時都已經被證明必然超標。由於後續加入的元素皆為非負數，那些已經超標的起點在未來只會變得更昂貴，絕無鹹魚翻身的可能。因此當前的 [left, right + 1) 就是以該 right 結尾時所能達到的最長合法區間。只要每一輪都用它來更新全域最大值，最終就能取得全域最優解。

初學者看到 for 迴圈內套了 while，常直覺誤判為 O(n²)。但請仔細計算指標步數：left 與 right 在整個演算法執行過程中都只會單向遞增，各自最多只會前進 n 次，因此 while 迴圈在全程的總執行次數上限就是 n 次，整體的總時間複雜度是極其優秀的 O(n)，輔助空間為 O(1)。在空間上我們只記錄兩個整數邊界，不隨便複製產生子陣列，若最終需要輸出實際子陣列內容，再依長度另計空間即可。

關鍵警示：負數反例破壞單調性。試想輸入為 [4, −3, 2]，budget = 3。若盲目套用上述規則：讀入 4 時總和超標，演算法會把 4 永久剔除，最終只能回傳長度為 2 的區間；但事實上整段陣列總和 4 + (−3) + 2 = 3 完全符合預算，真正最優解長度應該是 3。負數的存在使得「原本超標的區間在往後擴張時反而可能重新達標」，徹底摧毀了永久排除起點的數學邏輯。因此本函式嚴格禁止負數；如果面對混合正負數的任意連續子陣列和問題，必須改用前綴和搭配雜湊表（詳見第 03 章）。

在字串題目中，常見的「求不重複字元的最長子字串」同樣可以使用滑動視窗，只是判斷超標的條件改成了「當前字元是否曾出現過」，此時可透過記錄字元最後出現位置來加速左指標跳躍（詳見第 03 章）。它們背後共通的邏輯核心始終不變：新元素納入後，左端只需單向收縮就能重獲合法，且被排除的區間絕對不可能在後續產生更好的結果。

6. 前綴和：把一段相加換成兩點相減

LeetCode 303 · Range Sum Query - Immutable：將原題的包含式 [left,right] 轉為本節的 [left,right+1)。

在許多業務情境中，陣列本身是靜態不變的，但外界會頻繁發起成百上千次的區間總和查詢。如果每次查詢都傻傻地逐一迴圈加總，查詢次數一多系統就會不堪重負。解決之道是預先建構前綴和陣列 P：我們約定長度為 n + 1，令 P[0] = 0，且 P[i+1] = P[i] + nums[i]。此時 P[i] 精準代表了原陣列前 i 個元素的總和。於是，任意半開區間 nums[left:right] 的元素總和，就可以直接透過 P[right] − P[left] 於常數時間內瞬間算得。請注意：負數的存在完全不會破壞這個等式，因為前綴和利用的是加減法的可逆代數運算，而完全不依賴數值的單調性。

def build_prefix(nums: list[int]) -> list[int]:
    prefix = [0]
    for value in nums:
        prefix.append(prefix[-1] + value)
    return prefix


def range_sum(prefix: list[int], left: int, right: int) -> int:
    if not 0 <= left <= right < len(prefix):
        raise ValueError("區間必須符合 0 <= left <= right <= n")
    return prefix[right] - prefix[left]

驗證查詢：查 [1, 4) 得到 P[4] − P[1] = 7 − 3 = 4（對應 −2 + 5 + 1）；查整段 [0, 4) 得到 P[4] − P[0] = 7 − 0 = 7；查空區間 [2, 2) 得到 P[2] − P[2] = 0。統一由 P[0] = 0 做哨兵，程式碼完全不需要針對 left = 0 寫任何 if 特判。

核心不變量：在建立到第 i 個前綴邊界時，prefix[i] 的數值精準對應原陣列區間 [0, i) 的元素總和。查詢時利用代數關係把共同的歷史前綴相互抵銷，便留下了目標區間的淨總和。建表需要 O(n) 的時間與空間，之後面對任意 m 次查詢，每次都僅需 O(1)，總時間為 O(n + m)。請特別記住：這項優勢建立在「陣列資料不變」的假設上，若原始資料會動態修改，前綴和就需要整批重算；若需要支援動態單點修改與區間查詢，請見後續篇章的線段樹或樹狀陣列。

前綴技巧雖好，但不能盲目套用到所有聚合運算上。例如「區間最大值」就無法透過前綴資訊進行相減還原：因為知道前 10 個數的最大值是 100，又知道前 3 個數的最大值是 50，我們根本無法推斷出第 4 到第 10 個數的最大值是多少（減法無法逆轉最大值運算）。決定使用前綴摘要前，請先確認該運算是否具備「可減性（Invertibility）」。

7. 練習與解答

LeetCode 643 · Maximum Average Subarray I：最大總和除以固定長度 k，即為原題的最大平均值。

練習 1：全負數視窗。面對輸入 [−5, −2, −4]、k = 2，請手算 current 與 best 的變化軌跡。若在程式一開始將 best 慣性初始化為 0，會產生什麼致命錯誤？為什麼固定視窗允許負數，而可變預算視窗卻必須強制要求非負元素？

參考解答

第一個長度為 2 的視窗總和為 (−5) + (−2) = −7；滑動到下一個視窗時，更新為 −7 − (−5) + (−4) = −6，因此全域最大總和應回傳 −6。若將 best 錯誤初始化為 0，最終就會回傳從未存在過的 0。固定視窗之所以能接納負數，是因為它老老實實地遍歷了所有可能出現的長度 k 區間，只用加減維護滑動差值；而可變預算視窗仰賴「目前起點超標後，未來擴張必定更超標」的單調性來實施永久排除，負數的加入會徹底破壞這項推論前提。

LeetCode 209 · Minimum Size Subarray Sum：本節額外允許元素為 0。

練習 2：最短達標連續區間。給定非負整數陣列與 target > 0，請找出元素總和大於或等於 target 的最短非空連續子陣列長度；若完全無解則回傳 0。試說明它在更新 best 的時機點上，與前文的「最長不超標視窗」有何本質區別？

參考解答

當前視窗一旦滿足總和 ≥ target，就必須在收縮左端前立即記錄當前長度為候選解答，然後嘗試將 left 向右收縮以尋求更短的可能；直到總和跌破 target 不再滿足條件時，才停止收縮並等待下一個元素擴張。若等到 while 結束才記錄，留下來的反而是不達標的無效視窗。被排除並收縮掉的起點，在未來只會跟著 right 形成更長（即更劣）的區間，絕不可能刷新最短長度，因此可以放心丟棄。

def min_length_at_least(nums: list[int], target: int) -> int:
    """最短非空區間：元素非負、target > 0；無解回傳 0。"""
    if target <= 0 or any(value < 0 for value in nums):
        raise ValueError("target 必須為正，元素必須非負")
    left, total = 0, 0
    best = len(nums) + 1
    for right, value in enumerate(nums):
        total += value
        while total >= target:
            best = min(best, right - left + 1)
            total -= nums[left]
            left += 1
    return 0 if best == len(nums) + 1 else best

以 nums = [2, 1, 3, 1]、target = 4 為例，最短達標長度為 2（即 [1, 3]）。演算法時間複雜度為 O(n)，空間複雜度為 O(1)。本演算法允許陣列中包含 0，但 target 必須為嚴格正整數，以避免空區間判定發生混淆。

練習 3：外部查詢索引的規格轉換。若外部 API 傳入的查詢區間採用數學上常見的雙邊閉區間 [1, 3]（代表包含索引 1、2、3），我們該如何呼叫 range_sum 函式？如果外部查詢是單一元素的閉區間 [i, i]，又該如何處理？

參考解答

在呼叫 range_sum 之前，必須先將閉區間轉換為左閉右開的半開區間。對於 [1, 3]，對應的半開區間是 [1, 4)，因此呼叫 range_sum(prefix, 1, 4) 即可得到正確答案 4。許多初學者容易在單點查詢 [i, i] 上跌倒，請記住閉區間 [i, i] 包含一個元素，轉換後應為 [i, i + 1)，若誤傳 [i, i) 就會變成空區間而回傳 0。在軟體架構中，最佳實踐是在介面邊界層做一次統一的轉換，核心邏輯內部則始終堅定採用同一套區間標準。

練習 4：原地壓縮的記憶體行為。對陣列 [7, 7, 1, 7, 2] 執行刪除 7 的操作，請手算每一輪 read 與 write 指標的步進過程，並解釋為什麼不需要花額外功夫把被刪除的元素搬遷到陣列尾端。

參考解答

在處理各個位置後，write 指針的數值依序為 0、0、1、1、2；處理結束後，陣列前兩格的內容剛好是 [1, 2]。題目合約僅保證「回傳值 write 之前的前綴屬於有效資料」，對於 write 之後的記憶體區域並沒有任何保留或排序的承諾。額外進行元素交換或將垃圾資料移往尾端，不僅白白浪費時間，更可能破壞演算法的原地穩定性。
