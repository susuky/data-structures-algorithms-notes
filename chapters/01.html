01｜基礎：先說清楚，再把程式寫對

資料結構決定了資料在記憶體中如何組織，而演算法則是處理與轉換這些資料的具體步驟。學習演算法時，光是死記題型或背誦模板往往很難應付變化；真正重要的是在實作每一步時，都能清楚回答三件事：我們目前掌握了什麼資訊？下一步的推進為什麼是安全且正確的？以及整個過程到底要付出多少計算成本？本章建立的成本模型與正確性推理，將會貫穿後續的所有章節。

成本模型約定：本書範例皆以 Python 3.10+ 為基準。通常我們用 n 代表記憶體中的元素數量，並將一般的整數加減、比較與索引操作視為 O(1)。但若遇到超長字串、大整數運算或需要列舉所有答案的情境，就必須把字元長度、位元數以及輸出規模一併納入複雜度分析。

1. 從輸入與輸出合約開始

拿到題目的第一步，千萬別急著直接敲鍵盤寫程式，而是先釐清資料範圍與輸出規格。以看似最簡單的「找最大值」為例：如果輸入是空集合該如何處理？是否允許直接修改原始陣列？若有多個最大值同分，是要回傳哪一個？在動筆前先把這些邊界條件敲定，往往比過早糾結於該選哪種資料結構更有價值。此外，在設定變數時也要保持誠實：如果題目給了 n 個元素與 m 次查詢，分析時就該明確保留 n 與 m 兩個變數，除非題目明確保證兩者等價，否則不要直接混為一談。

  1. 輸入特性：資料是否已經排序？會不會出現負數、重複值或空值？資料是一次性全量給齊，還是像串流一樣陸續抵達？
  2. 輸出規格：要的是存在性（布林值）、統計個數、特定索引，還是具體的元素內容？甚至需要列出所有合法組合？請特別注意：「找出任意一組解」和「找出最早出現的一組解」是完全不同的合約。
  3. 限制與代價：是否允許原地修改原陣列？是否必須維持原本的相對順序？時間與額外記憶體之間的取捨權重為何？
  4. 基準解（Baseline）：先寫出一個邏輯絕對正確的小規模暴力解。它不僅能幫助你徹底想通題意，更是後續檢驗優化版本是否出錯的最佳對照組。

新手最常踩的坑之一，就是題目要求回傳索引，程式卻回傳了數值；或是為了方便處理而先排了序，卻忘記排序後元素的原有索引已經全被打亂。就算演算法跑得再快，只要輸出違反了合約規格，它就不是正確的解答。

2. Big O：把工作量寫成成長率

假設 T(n) 代表演算法在規模為 n 時執行的關鍵操作次數。數學上，T(n) = O(f(n)) 表示當 n 充分大時，存在一個固定的正常數 C，使得 T(n) ≤ C × f(n)。這代表 f(n) 是 T(n) 的漸近上界；而 Θ(f(n)) 則表示上下界緊密同階，Ω(f(n)) 代表漸近下界。雖然在面試與日常討論中，大家常習慣用「O(n)」來代指緊密的成長量級，但嚴格來說，線性函式在數學上同樣落在 O(n²) 的範圍內。因此在進行效能分析時，我們應該盡可能給出最緊確、最具資訊量的界。

舉例來說，3n + 20 屬於 Θ(n)，而 n² + 5n 則屬於 Θ(n²)。去掉低階項與常數係數，是為了將焦點放在輸入規模被放大時的工作量成長趨勢；但請記住，程式在實際執行時，那些低階操作依然真實存在。O(1) 表示操作次數不會隨著輸入規模膨脹；哪怕每次都固定做 10,000 次操作，在漸近意義上依然是常數時間。此外，兩個同樣被標記為 O(n) 的程式，實際執行時間可能大不相同，因為真實效能還會受到 Python 直譯器版本、記憶體配置、快取命中率與硬體架構的影響。

當輸入規模倍增時，線性模型的工作量只會跟著翻成兩倍，但平方模型卻會膨脹為四倍。對數的底數在漸近分析中只差一個常數倍率，因此實務上通常統一寫成 O(log n)。

討論時間複雜度時，還必須講清楚指的是哪一種場景：線性搜尋在第一格就命中是最佳情況 O(1)，完全找不到一路掃到底則是最壞情況 O(n)；如果討論平均時間，就必須明確給出輸入資料的機率分布假設。而攤銷時間則是把一連串連續操作中偶發的高昂成本，平均分攤到每一次操作上，它建立在嚴謹的總成本保證上，而不是僥倖假設遇到好運的輸入。例如 Python 的 list.append 在觸發動態擴容時雖然需要複製並搬移大量指標，但在連續追加的情境下，平均每次 append 的攤銷成本依然是穩定的 O(1)。

3. 逐步範例：巢狀迴圈不靠外觀判定

題意：輸入非負整數 n，回傳所有符合 0 ≤ j < i < n 的位置對數量；只回傳個數，不列出位置對。n 為負數時拋 ValueError。

下面的程式用來計算所有滿足 j < i 的位置對。我們只做累加計數，不建立任何暫存清單。外層迴圈在第 i 輪時，內層迴圈會剛好執行 i 次，因此整體的總執行次數為 0 + 1 + 2 + … + (n − 1) = n(n − 1)/2。

def count_position_pairs(n: int) -> int:
    """計算 0 <= j < i < n 的位置對數，不儲存所有位置對。"""
    if n < 0:
        raise ValueError("n 必須非負")
    pairs = 0
    for i in range(n):
        for j in range(i):
            pairs += 1
    return pairs

迴圈不變量：在外層迴圈開始第 i 輪時，pairs 已經精確算完了索引 0 到 i − 1 之間的所有合法配對，數值剛好等於 i(i − 1)/2。在本輪中，我們把目前的位置 i 分別與前面的 i 個位置進行配對，因此 pairs 恰好增加 i；當整個迴圈結束時，便不重不漏地算完全部 n 個位置。這種「先定義已完成的狀態，再證明當前推進步驟保持正確」的思維，是演算法正確性證明的核心方法。

本演算法的時間複雜度為 Θ(n²)，輔助空間為 O(1)。但請注意：如果題目要求把每一對結果都存進清單回傳，雖然計算時間依然是 Θ(n²)，但輸出空間就會直接暴增為 Θ(n²)。此外，兩個前後依序執行的單層迴圈是 O(n + n) = O(n)，而針對不同變數的雙層巢狀迴圈則可能是 O(nm)。絕不能一看到兩層 for 就直覺斷定它是 O(n²)，必須仔細檢視內部指標真正的步進次數。

另一個新手極易忽略的盲點是額外空間的消耗：排序時產生的臨時緩衝區、集合中儲存的鍵值、清單切片、遞迴呼叫時佔用的呼叫堆疊（Call Stack），以及 generator 尚未釋放的狀態，全都會佔用記憶體。宣稱演算法是「原地（in-place）」操作，並不代表額外空間就自動等於 O(1)，例如某些原地排序演算法依然需要對數級別的輔助呼叫堆疊。

5. 遞迴：縮小問題，也保留回來的位置

題意：輸入整數清單 nums，分別用線性掃描與遞迴分治回傳元素總和；空清單回傳 0，兩個版本都不修改原始輸入。

一個設計嚴謹且可靠的遞迴函式，必須同時具備四個關鍵要素：明確的參數定義、直接回傳的基本情況（Base Case）、每一步都嚴格縮小規模的子問題，以及將子問題答案正確合併的組合規則。在程式執行時，呼叫端會暫停在目前的執行點，等待子呼叫完成並回傳結果；所有尚未完成的函式狀態都會暫存在記憶體的呼叫堆疊中。在 Python 中，千萬不要依賴尾端遞迴最佳化（CPython 原生並不支援），鏈狀過深的遞迴很容易直接撞上遞迴深度上限（RecursionError）。

下面我們透過兩種不同的寫法來計算清單總和。線性版本依靠「total 始終等於目前已遍歷元素總和」的迴圈不變量；而遞迴版本則建立在「total(lo, hi) 回傳 nums[lo:hi] 區間和」的函式合約上。請特別注意：實作時我們只傳遞索引邊界，絕不真的在遞迴中進行清單切片。

def linear_total(nums: list[int]) -> int:
    total = 0
    for value in nums:
        total += value
    return total


def recursive_total(nums: list[int]) -> int:
    """以半開區間分治；不建立 nums 的切片。"""
    def total(lo: int, hi: int) -> int:
        if lo == hi:
            return 0
        if hi - lo == 1:
            return nums[lo]
        mid = (lo + hi) // 2
        left = total(lo, mid)
        right = total(mid, hi)
        return left + right

    return total(0, len(nums))

逐步追蹤 nums = [7, −2, 5, 4] 的呼叫與回傳過程：

執行階段當前堆疊中等待中的呼叫子呼叫回傳的結果
向左深入探底[0,4) → [0,2) → [0,1)抵達基本情況，回傳 7
完成左半部分[0,4) → [0,2)取得右子 [1,2) 的 −2，相加合為 5
完成右半部分[0,4) → [2,4)分別取得 5 與 4，相加合為 9
完成根節點匯總[0,4)左半 5 + 右半 9 = 14

正確性證明：當區間長度為 0 或 1 時，程式直接由基本情況回傳正確結果。若假設所有長度更短的子區間都能正確計算，由於左右子區間彼此互斥且完整覆蓋了原區間，兩者相加必然等於原區間的總和。又因為只要長度大於 1，切分出的兩個子區間長度都嚴格小於原長度，因此保證遞迴必定能收斂至基本情況而終止。這是標準基於區間長度的數學歸納法證明。

對於包含 n 個元素的非空輸入，遞迴樹共有 n 個葉節點，且每個內部節點都恰有兩個子節點，因此總呼叫次數剛好為 2n − 1，時間複雜度為 Θ(n)。在空間方面，任何時刻同時存活於記憶體中的，只有一條從根節點到葉節點的路徑，其深度為 O(log n)，因此輔助呼叫堆疊空間為 O(log n)；對於空輸入則是 O(1)。相較之下，前面的線性迴圈版同樣需要 Θ(n) 時間，但輔助空間只需要極致的 O(1)。

如果我們在每次遞迴時都貪圖方便寫出 nums[:mid] 與 nums[mid:] 進行陣列切片，那麼每一層所有切片的複製總長度都會達到 O(n)；在總共 O(log n) 層的遞迴樹下，整體時間複雜度就會從原本漂亮的 O(n) 惡化成 O(n log n)。而在深度優先搜尋的執行過程中，記憶體中同時存活的切片大小沿著呼叫路徑累計為 n + n/2 + n/4 + …，峰值空間同樣會膨脹到 O(n)。請時刻提醒自己：時間複雜度是累計全程的所有操作總和，而空間複雜度衡量的是同一時刻記憶體佔用的最大峰值。

6. 練習與解答

練習 1：count_position_pairs(5) 的回傳值是什麼？若題目只需要回傳總配對數，如何將原本的兩層迴圈簡化為常數次算術運算？這項改進在時間分析上有什麼先決假設？

參考解答

回傳值為 10。對於任意非負整數 n，直接回傳 n * (n − 1) // 2 即可。在固定字長的標準算術模型下，這種做法可以在 O(1) 時間與 O(1) 輔助空間內完成；但若 n 是位元數無上限的大整數，乘法運算的實際耗時就必須依位元長度重新分析，不能無條件宣稱與輸入大小完全無關。

練習 2：以下函式在輸入 n = 13 時會執行幾輪迴圈？為什麼緊確的時間複雜度是 Θ(log n)？當 n = 0 時的行為又是如何？

def halving_steps(n: int) -> int:
    if n < 0:
        raise ValueError("n 必須非負")
    steps = 0
    while n > 0:
        n //= 2
        steps += 1
    return steps
參考解答

變數 n 的數值變化依序為 13 → 6 → 3 → 1 → 0，總共執行 4 輪。當 n > 0 時，迴圈執行的總輪數剛好為 floor(log₂ n) + 1，因此在固定操作成本的整數模型下，時間複雜度為緊確的 Θ(log n)，空間複雜度為 O(1)。當 n = 0 時，條件不成立直接略過迴圈，回傳 0。由於每次迭代都使非負整數 n 嚴格減半，這就是演算法必定會終止的有力保證。

練習 3：如果要將 k 個文字片段拼接成一個總長度為 L 的完整字串，為什麼反覆執行 result = result + part 不是一個具有線性時間保證的好寫法？

參考解答

在 Python 中字串屬於不可變物件（immutable），我們必須保守地假設每次進行加號拼接時，系統都可能需要重新配置記憶體並完整複製既有的字串內容；若每個文字片段的長度相近，累計下來的複製成本很容易惡化到 Θ(k²)。雖然某些直譯器版本在特定情境下會有原地追加的私有最佳化，但我們絕不能將實作細節的巧合當成演算法的漸近保證。使用 "".join(tokens) 能夠明確向系統表達一次性建構的需求，時間複雜度為穩定的 O(k + L)，結果字串所需空間為 O(L)，底層實際編碼寬度則視字元內容而定。

def join_tokens(tokens: list[str]) -> str:
    return "".join(tokens)

練習 4：有人認為「既然這個遞迴樹最終會拆解出 n 個葉節點，那麼呼叫堆疊的空間複雜度必然就是 O(n)」。請以本章的分治加總程式為例進行反駁，並說明在什麼情況下的遞迴才會真正需要線性等級的呼叫堆疊空間。

參考解答

呼叫堆疊衡量的是程式執行期間，同一時間在記憶體中尚未返回的「單一條最深呼叫路徑」，而不是全樹所有節點的加總。在平衡二分的情況下，這條路徑的深度僅有 O(log n)。只有當遞迴結構退化成線性單鏈——例如每次呼叫僅把規模由 n 減少為 n − 1，且外層呼叫必須停留在原地等待內層呼叫完成時，堆疊才會層層堆疊達 n 層，此時空間複雜度才會是 O(n)。千萬不要把「全程累積的工作總量」與「同一瞬間並存的記憶體空間」混為一談。

7. 練習流程與驗證方法

在面對任何演算法題目時，建議大家養成一套嚴謹的解題循環：首先用自己的話精準重述題目的輸入輸出合約 → 在紙上畫出三到五個具體的小規模測資 → 先寫出無腦但邏輯絕對正確的暴力解 → 觀察運算過程中到底浪費了哪些重複工作 → 明確定出狀態定義與關鍵不變量 → 推導出漸近複雜度更好的優化方案 → 嘗試設計刁鑽的反例來質疑自己的想法 → 動手寫出乾淨的實作並跑通測試 → 隔天不看任何筆記重新自己默寫一次。唯有徹底想通「為什麼某些分支或元素可以被安全排除」，這套推理能力才能真正遷移到其他未曾見過的題目上；變數名稱寫作 l 還是 left 只是個人習慣，背後的邏輯不變量才是真正的精髓。

在測試階段，請務必養成主動覆蓋極端案例的習慣：空輸入、單一元素、所有元素皆相同、已經完全排好序、完全逆序、包含負數，以及預期答案不存在的情況。對於可以窮舉的小規模問題，撰寫一段自動化腳本，將優化解與暴力解的輸出進行對照驗證（Stress Testing），通常比手動肉眼盯著幾個幸運範例測試，更能及早揪出那些致命的邊界邏輯錯誤。

章末思考與決策：解題分析時，先明確定義代表輸入規模的變數，再仔細計算底層的真實工作量；遇到看似簡潔的切片、字串拼接或比較操作時，務必在腦中將它們背後的隱藏成本展開；撰寫遞迴時，永遠第一時間確認基本情況與嚴格縮小的推進規則；討論空間複雜度時，要清晰切分輸入資料、最終輸出與額外輔助空間。在接下來的第二章中，我們將進入雙指標與滑動視窗的世界，屆時我們會廣泛運用「每個元素最多被指針造訪幾次」來證明演算法具備優秀的線性時間複雜度。
